01

Idea & Research

Two domain challenges motivated this lakehouse: first, raw Formula 1 points cannot be summed across decades because the FIA inflated win values by 312.5% between 1950 and 2010; second, the upstream dataset arrives in 8 incompatible file structures that require idempotent weekly cutover loading after every Grand Prix.

8 Schemas [2]Across CSVs, single-line JSON, nested STRUCT JSON, multi-line JSON, and split multi-file directories
~500k+ [2]Granular lap-time records across 70+ seasons joined to evaluate driver & constructor dominance

Standardise cross-era dominance with 11 - position and sample-size floors

Decision
In the Gold table f1_gold.calculated_race_results, compute 11 - results.position AS calculated_points for all top-10 finishers (P1 = 10, P10 = 1) while preserving official FIA points in f1_gold.race_results for single-season championship classifications.
Alternative
Rank all-time drivers and constructors directly from SUM(results.points) or AVG(results.points).
Why not that
Both raw metrics are skewed across eras: SUM(points) rewards post-2010 drivers who race 22–24 times a season for 25 points a win, while raw AVG(points) without a sample-size floor puts one-off 1950s Indy 500 entrants above 7-time World Champions.
Trade-off accepted
Filtering WHERE position <= 10 and HAVING COUNT(1) >= 50 excludes mechanical retirements and short-career prodigies unless the race threshold parameter is lowered for decade-specific views.
02

Planning & Architecture

The architecture implements a three-tier Medallion Lakehouse (bronze, silver, gold) on Azure Data Lake Storage Gen2 and Azure Databricks, orchestrated by a metadata-driven Azure Data Factory (ADF) parent pipeline.

Azure Databricks Medallion Lakehouse orchestrated by Azure Data Factory (Project_solution_architect.png & ADF_parent_pipeline.png).

Three-stage engineering progression: from DROP PARTITION to Delta Lake MERGE

Approach 1 (Evaluated)
Collecting distinct race_id values to the Spark driver and running ALTER TABLE f1_silver.results DROP IF EXISTS PARTITION (race_id = ...) in a loop before appending Parquet. Rejected because driver-side loops and sequential DDL calls are non-atomic if a job fails mid-loop.
Approach 2 (Intermediate)
Dynamic Partition Overwrite (spark.sql.sources.partitionOverwriteMode = dynamic + insertInto via overwrite_partition() in common_functions.py). Faster than Approach 1, but overwrites entire partitions on raw Parquet without ACID time-travel or row-level upserts.
Production Choice
Delta Lake MERGE INTO via merge_delta_data() with spark.databricks.optimizer.dynamicPartitionPruning.enabled = true. Matches on (result_id, race_id) to update amended rows in place and insert new race weekends atomically.
Trade-off accepted
Delta MERGE carries higher write amplification than blind append, so the merge condition explicitly includes the partition key (targets.race_id = source.race_id) to trigger Dynamic Partition Pruning.
03

Requirements Analysis

Ingesting 70+ years of historical sports records exposes edge cases in the raw data that break naive ETL pipelines — most notably 1950s shared-car rules that violate modern primary-key assumptions.

Deduplicating 1950s shared-car entries before executing Delta Lake MERGE INTO

The data anomaly
In the 1950s Formula 1 World Championship, FIA regulations permitted two teammates to share a single car during a Grand Prix (or one driver to take over multiple cars in the same race). As a result, raw results.json contains multiple records with the exact same (driver_id, race_id) pair.
Why it breaks Delta Merge
Delta Lake's MERGE INTO requires the source DataFrame to be unique on the merge key; otherwise Spark throws UnsupportedOperationException: Cannot perform Merge as multiple source rows matched and attempted to modify the same target row.
Engineering Solution
Enforce results_deduped_df = results_final_df.dropDuplicates(["driver_id", "race_id"]) in 5.ingest_results_file.py prior to calling merge_delta_data().
Trade-off accepted
Dropping secondary shared-car entries loses the secondary classification record for a handful of 1950s races in exchange for a strict (driver_id, race_id) grain across Silver and Gold.

04

Schema & Data Design

The Medallion relational model (RaceResults_ERD.png) enforces explicit PySpark StructType definitions at the Bronze-to-Silver boundary so schema drift fails fast and lap-time formatting is preserved accurately.

Key Schema & Ingestion Design Decisions

Qualifying Lap Strings
Formula1/ingestion/8.ingest_qualifying_file.py: Defines qualifyId and constructorId to match the raw multi-line JSON keys in qualifying_split_*.json, and types q1, q2, and q3 as StringType() so formatted lap-time strings like "1:26.572" are preserved without NULL coercion.
Reusable Delta Utilities
Formula1/includes/common_functions.py: Centralizes add_ingestion_date(), re_arrange_partition_column(), df_column_to_list(), and merge_delta_data() so all 8 Silver notebooks and 4 Gold transformations share a single tested library via %run "../includes/common_functions".
Results Schema & Lineage
Formula1/ingestion/5.ingest_results_file.py: Enforces an 18-column StructType schema, normalizes camelCase fields (raceId → race_id, positionText → position_text), attaches file_date and data_source lineage columns, and drops redundant statusId.
Gold Upsert Mart
Formula1/transformed/4.calculated_race_results.py: Materializes f1_gold.calculated_race_results as a managed Delta table and executes an idempotent MERGE INTO on (race_id, driver_id) for every cutover batch.
05

PySpark Development

Below is the core incremental merge and partition utility module in Formula1/includes/common_functions.py that powers both Silver ingestion and Gold championship aggregations.

Shared Delta Lake & Partition Library (Formula1/includes/common_functions.py)

def re_arrange_partition_column(input_df, partition_column):
    column_list = []
    for column_name in input_df.schema.names:
        if column_name != partition_column:
            column_list.append(column_name)
    column_list.append(partition_column)
    return input_df.select(column_list)

def df_column_to_list(input_df, column_name):
    df_row_list = input_df.select(column_name).distinct().collect()
    return [row[column_name] for row in df_row_list]

def merge_delta_data(input_df, db_name, table_name, folder_path, merge_condition, partition_column):
    from delta.tables import DeltaTable
    spark.conf.set("spark.databricks.optimizer.dynamicPartitionPruning.enabled", "true")
    if (spark._jsparkSession.catalog().tableExists(f"{db_name}.{table_name}")):
        deltaTable = DeltaTable.forPath(spark, f"{folder_path}/{table_name}")
        deltaTable.alias("targets").merge(
            input_df.alias("source"),
            merge_condition)\
            .whenMatchedUpdateAll()\
            .whenNotMatchedInsertAll()\
            .execute()
    else:
        input_df.write.mode("overwrite").partitionBy(partition_column).format("delta").saveAsTable(f"{db_name}.{table_name}")

08

Operations & Ecosystem Evolution

Operating a sports analytics lakehouse in production requires adapting to upstream API lifecycle changes — most notably the retirement of the historical Ergast Developer API at the close of the 2024 season.

Upstream Continuity: Jolpica-F1 & FastF1 High-Frequency Telemetry

Upstream Context
Following the scheduled sunset of the legacy Ergast API after 15 years of service, the lakehouse ingestion contract is designed so the Bronze landing structure remains decoupled from the upstream HTTP host.
Schema-Compatible Continuity
Pointing the ADF ingestion source to Jolpica-F1 (the schema-compatible open-source successor to Ergast covering current FIA seasons) feeds the exact same 8 Bronze schemas without changing downstream Silver or Gold PySpark logic.
Telemetry Enrichment
Extends the Silver layer with FastF1 / OpenF1 3.7 Hz car telemetry (speed trace, throttle, brake, DRS activation, and tyre compound stint degradation) joined on (race_id, driver_id, lap).
