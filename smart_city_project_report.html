Idea & Research

Why model a connected vehicle traveling from London (51.5074, -0.1278) to Birmingham (52.4862, -1.8904)? Because the M1/M6 spine is the UK's heaviest freight and commuter corridor — and traditional single-sensor highway monitoring fails when weather, congestion, and emergency incidents interact.

101 hrs [1]Lost per driver annually in London (#1 most congested city in Europe) and 59 hrs/yr in Birmingham
33% [2]Reduction in severe road incident mortality when emergency dispatch occurs inside the 15-minute Golden Window

The pipeline models a connected vehicle traversing the 100-segment trajectory between the UK's #1 and #3 most congested urban hubs.

Why 5 fused streams beat isolated road loops

Mean time to classify incident cause (minutes) [2]

Inductive loops detect a drop in speed (24.88 mph) but cannot tell whether the cause is heavy rain, a multi-car collision, or an active fire without fused context.

Corridor incident distribution

Observed distribution in Amazon QuickSight (City_Analysis.png)

High-frequency incident generation stress-tests downstream alerting, watermark state retention, and S3 partitioning.

Co-ingest 5 domain streams per vehicle tick rather than a single monolithic payload

Decision
Decompose urban telemetry into five dedicated Kafka topics — vehicle_data, gps_data, traffic_data, weather_data, and emergency_data — emitted concurrently as the vehicle progresses along the London–Birmingham route.
Alternative
Emit one wide, denormalised JSON message per tick containing vehicle OBD-II telemetry, GPS, camera snapshot, weather, and emergency status in a single topic.
Why not that
In a real municipal deployment, these five signals originate from completely different physical subsystems with different sampling rates and payload sizes (e.g., an onboard CAN-bus emits speed every second, whereas roadside ANPR cameras and municipal weather stations update asynchronously). Coupling them at the producer level breaks modularity.
Trade-off accepted
Splitting into five topics requires explicit schema governance, consistent entity partitioning (deviceId), and downstream watermarked join coordination in Spark and Redshift.
02

Planning & Architecture

The architecture pairs containerized local stream ingestion (Dockerized Confluent Kafka + Bitnami Spark 3.5 cluster) with managed AWS cloud storage, cataloging, and analytics (S3, Glue, Athena, Redshift, QuickSight).

End-to-end topology: Python IoT generators push 5 streams into a Dockerized Confluent Kafka broker; Spark 3.5 Structured Streaming writes both the 5 raw Bronze Parquet streams and the joined Silver corridor stream to S3.

Dual-tier streaming output: 5 raw Bronze S3 sinks plus a joined Silver corridor stream

Decision
Persist each of the five Kafka topics independently to S3 as an immutable Bronze replay layer (query1–query5) while simultaneously executing a 6th watermarked stream-stream join query (query6) that writes a unified Silver corridor table (silver_corridor_telemetry).
Alternative
Only write the joined stream to S3, or only write the five unjoined topics and defer all joining to downstream BI queries.
Why not that
Dropping the raw streams sacrifices replayability if join logic changes later; conversely, leaving all five streams completely unjoined forces every Athena or QuickSight query to perform expensive multi-table timestamp range joins at read time.
Trade-off accepted
Stream-stream joins hold state in Spark executors for the duration of the 2-minute watermark window, increasing memory usage on the 1 GB Docker workers — a trade-off bounded by strict watermarking and 60-second micro-batch triggers.
Running Managed Kafka (Amazon MSK) and Managed Spark (AWS EMR or Glue Streaming) 24/7 quickly burns through cloud budgets. Running Confluent Kafka 7.4.0, ZooKeeper, and a 3-node Bitnami Spark 3.5 cluster inside local Docker Compose while persisting output to real AWS S3, Glue, and Athena demonstrates full cloud integration without idle cluster burn.
Athena queries S3 Parquet directly via the Glue Data Catalog with zero infrastructure warm-up ($5 per TB scanned), ideal for rapid SQL validation. Redshift serves the dimensional star schema (ERD_Diagram.png) where high-concurrency QuickSight dashboards join vehicle_data against the four supporting tables.
Each streaming query in spark-city.py isolates its write-ahead offset log under s3a://spark-streaming-data-2025/checkpoints/<topic_name>. If the emergency stream fails or restarts, Spark resumes from the exact Kafka offset committed for that sink without corrupting the other streams.

Requirements Analysis

A credible data engineering report separates what the simulator genuinely tests (multi-topic throughput, watermarked S3A sinks, schema evolution) from where synthetic data simplifies reality.

Deterministic trajectory simulation (random.seed(45)) as a reproducible benchmark

Decision
Simulate a Ford Focus ST (Vehicle-123) moving from London to Birmingham in 100 linear coordinate steps (LATITUDE_INCREMENT = +0.009788°, LONGITUDE_INCREMENT = -0.017626°) plus ±0.0005° GPS jitter and 30–60s logical clock increments every 3 wall-clock seconds.
Why
Fixing random.seed(45) in jobs/main.py makes the telemetry sequence reproducible across runs, allowing deterministic verification of downstream aggregations (such as the 24.88 mph average speed validated in QuickSight) and synchronizing GPS speed directly with vehicle speed on every tick.
Trade-off accepted
Prioritises deterministic infrastructure and streaming pipeline verification while preserving exact reproducibility with the published QuickSight analysis.

Data Engineer

Analytics / ML Engineer

Having synchronized vehicle speed, GPS coordinates, weather (precipitation, wind speed, AQI), and incident logs linked by deviceId and event window creates a clean feature store for travel-time prediction and anomaly detection.

City Operations Director

Instead of waiting for fragmented reports from highway patrol, weather stations, and traffic cameras, control-room operators get a single QuickSight view showing active vs. resolved emergencies alongside live corridor speed and air quality.

04

Design

Data modeling bridges the raw streaming JSON payloads in Kafka with the relational star schema designed for Redshift and QuickSight (ERD_Diagram.png).

Star Schema Entity Relationship Diagram: all five tables share deviceId + timestamp as the natural composite join key for corridor analytics, while decomposing coordinates into typed latitude and longitude columns.

Explicit latitude & longitude DoubleType columns over untyped coordinate tuples

Decision
Emit explicit latitude: float and longitude: float fields in jobs/main.py and enforce StructField("latitude", DoubleType()) + StructField("longitude", DoubleType()) across all schemas in jobs/spark-city.py.
Alternative
Pass coordinates only as a 2-element tuple (lat, lon) or string in a single location column.
Why not that
If a JSON array [51.517, -0.145] is parsed against a numeric DoubleType() field in Spark's from_json(), Spark silently coerces the value to NULL. Decomposing coordinates into explicit doubles eliminates silent NULL coercion and allows Amazon QuickSight to plot geospatial points natively without SQL string splitting.

Development

The implementation spans three core modules: docker-compose.yml (container cluster infrastructure), jobs/main.py (IoT telemetry producer), and jobs/spark-city.py (Spark Structured Streaming consumer, watermarked join, and S3A writer).

Key Engineering Implementation Highlights in jobs/

jobs/main.py
Keys produce_data_to_kafka() by str(data['deviceId']) so all events for a vehicle land on the same Kafka partition in chronological order; emits explicit latitude and longitude floats; synchronizes gps_data speed with vehicle_data['speed']; and passes lightweight S3 snapshot URIs rather than raw Base64 image blobs.
jobs/spark-city.py
Enforces StructType schemas across all 5 streams with a 2-minute watermark, writes raw streams to S3 Bronze, and executes a watermarked stream-stream join (corridorSilverDF) writing enriched rows to s3a://.../data/silver_corridor_telemetry on a 60-second micro-batch trigger.
jobs/config.py
Loads AWS_ACCESS_KEY, AWS_SECRET_KEY, and S3_BUCKET via os.getenv() so cloud credentials remain decoupled from source control.

Stream Consumer & Watermarked Join (jobs/spark-city.py)

corridorSilverDF = (
    vehicleDF
    .join(
        weatherDF,
        expr("""
            vehicle.deviceId = weather.deviceId AND
            weather.timestamp >= vehicle.timestamp - interval 1 minute AND
            weather.timestamp <= vehicle.timestamp + interval 1 minute
        """),
        "inner"
    )
    .join(
        emergencyDF,
        expr("""
            vehicle.deviceId = emergency.deviceId AND
            emergency.timestamp >= vehicle.timestamp - interval 1 minute AND
            emergency.timestamp <= vehicle.timestamp + interval 1 minute
        """),
        "inner"
    )
    .select(
        col("vehicle.id").alias("vehicle_event_id"),
        col("vehicle.deviceId").alias("device_id"),
        col("vehicle.timestamp").alias("event_timestamp"),
        col("vehicle.latitude").alias("latitude"),
        col("vehicle.longitude").alias("longitude"),
        col("vehicle.speed").alias("speed_mph"),
        col("weather.temperature").alias("temperature_c"),
        col("weather.weatherCondition").alias("weather_condition"),
        col("weather.airQualityIndex").alias("air_quality_index"),
        col("emergency.type").alias("incident_type"),
        col("emergency.status").alias("incident_status")
    )

Maintenance & Cost Governance

Operating a streaming pipeline over extended periods exposes storage and query-cost challenges — chief among them the S3 small-file problem.

Preventing the S3 "Small-File Problem" with 60-Second Micro-Batch Triggers

The operational risk
An unthrottled writeStream query executes a new micro-batch as soon as the previous one finishes — writing a tiny Parquet file to S3 every 3 seconds per topic (6,000+ small files per hour across 5 topics).
Why it hurts
Amazon Athena query latency and S3 GET/LIST API charges scale with object count, not just byte volume. Thousands of 4 KB Parquet files severely degrade Athena and Glue Crawler performance.
Implemented Mitigation
Configured .trigger(processingTime='60 seconds') in streamWriter() inside jobs/spark-city.py, reducing S3 file creation by 20x while maintaining sub-minute dashboard freshness.
